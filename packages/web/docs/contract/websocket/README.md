## 每份文档的结构

开头是功能域的简介和一张表：上行和下行各几种、处理代码在 `packages/web/src/server.ts` 的哪些行、运行时方法在哪个文件。然后分两节：上行消息、下行消息。每种消息一个条目，标题是消息名。

### 上行消息的条目

先是一段说明：这条消息做什么，什么时候用，有什么前置条件。然后是一张四行的表：

| 行 | 含义 |
| --- | --- |
| 字段 | 字段名、必填还是可选、类型，以及类型定义里的注释 |
| 回复请求方 | 只发给发出这条消息的连接的消息。处理可能失败时这里有 `error` |
| 广播 | 发给所有已连接控制台的消息，包括发出消息的那个 |
| 失败文案 | 处理这条消息时可能回给浏览器的 `error` 文案，逐条列出。花括号是占位符，`{…}` 表示那个值不是简单的变量名 |

「回复请求方」「广播」「失败文案」三行不是手写的：测试从处理代码里读出来，再和文档比对，所以它们列全了处理分支里写明的每一条。有两点要留意：

- 一条文案只在处理分支、它调用的方法以及再往下一层里找。藏得更深的异常到浏览器时是「异常的原文」，不在这一行里；其中在实测中出现过的已经补上。
- 有的消息失败时不回 `error`，而是回一条结果消息，`ok` 为 `false`、`error` 是原因。这类失败不写在「失败文案」一行，写在表后面的句子里。

表后面是一两句话，依次说明：

1. 处理的结果怎么回来：回了什么，广播了什么。
2. 通过状态通知发出的广播（多数是 `snapshot`）只在状态实际变化时才有，什么都没变时不发。
3. 失败怎么回来：回 `error`；或者回一条带 `ok: false` 的结果消息，原因有哪些；或者把异常的原文作为 `error` 的文案。

最后是一个 JSON 样例。

### 下行消息的条目

先是一段说明：这条消息带什么，前端用它做什么。然后是一张表，`发送时机` 一行列出它在哪些情况下发出：哪些上行消息会触发它，哪些运行时事件会触发它，是否在连接建立时推送。表后面是一个 JSON 样例。

## JSON 样例

每条的样例都经过了编译器对消息类型的校验：必填字段齐全，字段名和取值类型正确。它们由 `packages/web/test/contract/examples/` 下的文件提供，和文档里的是同一份。

样例里的主机、路径、ID 都是示意值。真实数据以类型为准。

## 字段形状

条目里的「字段」一行是用来说明含义的，字段的精确定义在类型文件里。每份文档开头给出了处理代码和涉及的类型在哪个文件、哪些行。

- 服务端视角：`packages/web/src/protocol.ts`。下行消息以它为准。
- 浏览器视角：`packages/web/webui/src/types.ts`。上行消息以它为准。

两份类型有 11 种下行消息存在已知差异，取舍见 [type-alignment.md](type-alignment.md)。

## 怎么读一条消息

以 `save_model_entry` 为例：

1. 在 [models.md](models.md) 找到 `### \`save_model_entry\``。
2. 读说明和「字段」一行，知道浏览器会发什么。
3. 看「回复请求方」和「广播」：成功时回 `model_library`，并广播一个 `snapshot`。
4. 看「失败文案」：出错时回 `error`，文案是其中一条。
5. 对照 JSON 样例写出收发的数据。
