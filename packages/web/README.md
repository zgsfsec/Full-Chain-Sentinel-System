# Full Chain Sentinel Web

全链哨兵 的 Web 控制台：内嵌 pi coding-agent SDK 的 HTTP + WebSocket 服务，以及浏览器端中英文控制台界面（默认中文）。

## 功能

- **控制台布局**：左侧分组侧边菜单（工作台 / 系统）。对话、项目、设置、关于是页面，导航只有侧边栏一个入口；「文件」与「子代理」不再是独立页面，而是从对话页工具栏打开的弹窗，因为它们都是针对当前会话/项目的操作，放在侧边栏会割裂上下文。项目选择器固定在侧边栏顶部，因为所有页面都作用于当前项目的容器
- 流式对话（文本 + 思考过程）与工具执行卡片实时展示（含长命令执行中的滚动输出）
- **中英文切换**：默认中文；侧栏底部、登录页与授权承诺页都能切换。界面与服务端返回的提示、错误、诊断、报告都有英文版本；AI 生成的对话、结论与用户输入保持原文。选择存 `<配置目录>/ui-config.json`，由服务端同步到所有浏览器，登录前通过 `/api/ui-language` 读取
- 三执行模式：
  - **审批模式（默认）**：bash 命令执行前弹出审批，可编辑命令后放行或拒绝
  - **自动执行**：命令直接运行，不做拦截
  - **AI 审批**：每条 bash 命令执行前由守门员模型判一次 `ALLOW` / `BLOCK`，判定失败或超时一律放行（见下）
- **AI 审批（守门员）**：判定只针对这一条命令的直接效果，拦截范围限定在会直接破坏目标可用性、业务数据完整性或系统配置的六类操作——改/重置密码、改服务器或服务配置（`/etc`、`nginx.conf`、`my.cnf`、防火墙、计划任务）、改用户与权限（`useradd` / `GRANT` / 放宽 shadow 权限）、删除或篡改真实业务数据（业务接口的 DELETE/PUT/PATCH、`DROP TABLE` / `TRUNCATE` / `rm` 重要文件）、停止或重启业务服务（`systemctl stop` / `kill` / `reboot`）、大规模压测（`hping3 --flood` / 高并发 `ab`）。授权渗透的正常手段即使带写动作也放行：注入类 payload、文件上传（含 webshell）、弱口令爆破、扫描枚举、通过路径遍历或 `file://` 读 `/etc/passwd` 等敏感文件。判 `BLOCK` 时命令**不执行**，理由回给模型（提示换一种不破坏目标的方式，或请操作员在审批 / 自动模式下执行），**不重放**。判定失败、超时、回复无法解析都按**放行**处理并记为「请求失败」，界面顶部是一条黄色提示条（「守门模型不可用，已放行 N 次」），不会因为守门员掉线把工作卡死。**AI 模式下命令前缀白名单失效**：每条命令都过模型，不做本地短路
- **模型库**（设置 → 模型）：页面以「角色」为主——**主模型**、**守门模型**、**漏洞评审**、**监督模型**、**指挥端点**五个角色各自从模型库里挑一条模型，其余角色可以选「跟随主模型」，改主模型时它们一起换。下面才是模型库本身：一条模型 = 一个（Base URL + 模型 ID + API Key），可加、编辑、复制（同地址再开一条靠它）、测试连接、删除；被任何角色引用的模型**删不掉**，页面会点名是哪些角色在用。密钥明文存在 `~/.sentinel/agent/model-library.json`（0600），前端不回显（编辑时留空表示不改，另有「清除已保存的密钥」把端点改成无鉴权）。老版本的三个固定槽位（主端点 / 指挥官端点 / 守门端点）在首次打开这个页面时自动迁成模型库条目，角色指向关系按旧回落链还原
- **守门模型**（设置 → 模型 → 角色）：AI 审批的判定端点，默认「跟随主模型」。页面写明当前生效的是哪条模型；可设判定超时（默认 15 秒）与并发上限（默认不限，最多 64），并有「测试判定」用一条样例命令验证端点。判定调用固定 `temperature: 0`、`max_tokens: 128`，一次命令一次调用。**改完立即生效**，不会重建正在运行的会话
- **守门审计**（侧栏「工作台 → 守门审计」）：只读的判定流水。统计块给出 拦截 / 放行 / 请求失败 / 拦截率 / 平均耗时 / 最近 24 小时 / 判定 tokens / 最近一次成功；可按判定、来源（主代理 / 子代理 / 工程任务）、时间窗口、项目、关键字过滤；表格逐条列出时间、判定、来源、命令、理由、耗时，展开一行看完整命令、cwd、模型来源与 tokens，并可直接跳到发起该命令的会话。`ALLOW` 也记录，记录存 `<配置目录>/gatekeeper.db`（SQLite）永久保留，**判定消耗的 tokens 只出现在这一页**，不计入会话或工程的用量；判定失败时页面顶部显示最近一次错误
- **监督**（会话开始前点输入框上方的「监督」；侧栏「工作台 → 监督」看全部审计）：会话级开关，不点就不采集。可选择「稳健交付 / 漏洞验证 / 红队推进 / 低噪声 / 不测危险接口」五种监督策略，可同时选多个，也可在「设置 → 模型 → 监督 → 自定义策略」里基于预设新建命名策略（名称、一句话说明、关注点与建议风格），并可写 200 字内的会话补充说明；策略只改变监督关注点和建议风格，不放宽安全规则。自定义策略在开启监督时快照到会话，之后修改或删除不影响已经开启的监督。每 20 次工具调用，或出现同一调用重复 3 次、连续 10 次没有新证据、连续 3 次报错时，独立的「监督模型」读取调用参数与结果摘要（不读完整输出），输出阶段、意图、已测试、已排除、进度判断和下一步。观察模式只在可收起的悬浮窗里显示状态、episode、最近调用和日志；介入模式可选自动发送或确认后发送，只注入一条带「非操作员指令」标签的建议，**不阻断**任何工具调用。收起悬浮窗不停止监督，必须显式点「停止监督」；停止后本次会话不能恢复。审计存 `<配置目录>/supervisor.db`，当前状态写入会话 JSONL，完整工具输出仍按 `callId` 从会话读取；删除项目连带删除审计
- **模式作用域**：模式分「全局默认」与「本会话覆盖」两层。工具条上的三态开关只改当前会话，存在会话文件的 `custom` 条目 `zg-mode` 里，重开、重建会话或 fork 都保留；设置 → 模型 里的开关改的是全局默认，新会话跟随它，已有覆盖的会话不受影响
- **子代理（spawn_agent）**：主代理可将独立子任务（如单主机侦察）委派给隔离子会话并行执行。子代理的工具集与本会话一致（含扩展提供的 codemode / tool_search / MCP 工具），再按「设置 → 权限」中给子代理勾选的开关收窄（永远是主 Agent 的子集）；bash 走与本会话同一个门（审批弹窗标注来源；AI 模式下同样过守门员，审计里记为「子代理」）；唯一永远不给的是 spawn_agent，因此不能再派生子代理
- 审批队列：并发工具调用逐条列出，可单条批准（可编辑）、全部批准、全部拒绝；支持「本会话自动放行此前缀」与命令前缀白名单（复合命令永不白名单放行；仅审批模式有效）
- **会话状态**（人工标记）：侧栏会话列表的每一行右侧有一个彩色标签，点它即可把会话标成 待跟进 / 进行中 / 已完成 / 已忽略（再点一次同一项或选「无状态」清除）。对话页顶部工具条有同一个入口，标的是当前会话。列表头可切 全部 / 未完成，「未完成」隐藏已完成与已忽略并显示 `N / M 个会话`。状态存在会话文件的 `custom` 条目里（`zg-status`），跟着会话走、fork 会继承、重启不丢，并且**不进模型上下文**：它只是操作员自己的备忘，模型看不到
- **设置页**（侧栏「系统 → 设置」，点击「设置」行展开/收起，展开时进入「模型」）：分「模型」「通知」「权限」「预设 Agent」「POC 订阅」「安全」「资产测绘」「MCP」「环境」等页面。模型分区配置 OpenAI 兼容端点，保存前一键验证，失败给出具体原因（超时 / 401 / 404 路径 / 模型不存在）与建议；空 API Key 的本地端点可直接使用
- **Agent 权限**（设置页「权限」）：主 Agent 与子 Agent 各一组开关（read / bash / edit / write / codemode / tool_search / MCP / spawn_agent / vuln_submit / vuln_read），全局保存在 `~/.sentinel/agent/permissions.json`，另有「标准 / 只读侦察 / 全部禁用」三个预设。子代理的权限永远是主 Agent 的子集，且永远拿不到 spawn_agent——否则主 Agent 关掉 bash 后只要派一个子代理就绕过了自己的限制。保存后立即重建所有活动会话（历史保留），有运行中的会话会拒绝保存并要求先中止。禁用是通过 SDK 的 `excludeTools` 在注册阶段剔除工具实现的，因此模型看不到、tool_search 搜不到、历史记录恢复不了、codemode 也调不到；页面同时列出当前会话实际挂载的工具，便于核对。**旧配置文件里没有的开关按「关闭」读取**：文件早于该开关存在，操作员从未同意过它，新增能力不能悄悄放宽既有配置；文件缺失或损坏仍按「全部启用」处理（那是全新安装）
- **环境页**（设置页「环境」）：进入页面或点「复检」时检查 Docker 命令行、守护进程、`sentinel:latest` 镜像、镜像与宿主架构是否一致、一次性容器能否启动、项目容器是否都在运行、代理镜像与 sidecar 是否就绪（含 sidecar 被重启过导致的 netns 失效、以及容器还在跑旧档案配置）、项目目录与配置目录是否可写、剩余磁盘空间、模型端点是否配置、构建镜像需要的网络。每项给出状态（通过 / 警告 / 失败 / 跳过）、实测值和修复建议，「复制诊断」把整份报告复制成文本
- **构建源**（设置页「环境」→ 构建源）：基础镜像可换成国内加速站（如 `docker.m.daocloud.io`，只填 registry 会自动补 `kalilinux/kali-rolling:latest`）或内网 registry，apt / pip / npm / go 可分别指向镜像源，另有「中国镜像源」一键预设（清华 apt、清华 pip、npmmirror、goproxy.cn）。这些值作为 `docker build --build-arg` 烘焙进镜像，所以保存后要重建镜像；pip / npm / go 三项同时写进镜像里的 `/etc/pip.conf`、`/root/.npmrc`、`/root/.config/go/env`，容器内运行时执行 `pip install` 等也走镜像源。留空即官方源，保存在 `~/.sentinel/agent/sources.json`，环境页的「构建源」检查项会列出下次构建实际使用的值
- **容器网络**（设置页「环境」→ 容器网络）：新建与重建的项目容器用哪种网络，默认 **host**——容器直接用宿主机的网络栈，里面起的监听端口（反向 shell、payload 服务、handler）目标机器能连回来，`127.0.0.1` 就是宿主机（Burp、本地靶场、控制台本身），内网、VPN 与内网 DNS 也是真实的；代价是与宿主机抢端口，且没有 Docker 的网络隔离。可切回 **bridge**（Docker 默认隔离：容器有自己的地址、只经 `host.docker.internal` 访问宿主机、不对外发布端口，目标连不回容器里的监听）。设置存在 `~/.sentinel/agent/container-network.json`，只影响之后新建或重建的容器，环境页的「项目容器」检查项会写明运行中的容器实际用哪个网络；host 模式不再授予 `NET_ADMIN`（那在宿主机命名空间里等于能改宿主机网络），`NET_RAW` 保留
- **自定义代理**（侧栏「代理」页 + 项目页每行的「代理设置…」+ 侧栏项目选择器每行的代理按钮）：让项目容器的出站流量走自己的代理。代理是**命名档案**：在「代理」页新建、编辑、删除，每个档案二选一地描述出口——**SOCKS5 / HTTP 地址**（类型、地址、端口、可选账号密码，HTTP 可开 HTTPS 上游；`socks5://1.2.3.4:1080` 这种整串能直接粘，端口会自己拆出来），或**订阅链接**（见下一条）。**默认代理**（新项目与「跟随默认」的项目用它，`不使用` 表示默认直连）与 **sidecar 镜像**（默认 `ghcr.io/sagernet/sing-box:v1.13.15`，可改成可达的镜像源，点「拉取镜像」执行 `docker pull`）不在这一页，而在**设置 → 环境 →「容器网络与代理」**——和容器网络**同一张卡、同一个「保存」**：容器要么走宿主机网络要么挂 sidecar，挂哪个 sidecar、用哪个镜像，本来就是同一个决定；分成两张卡要保存两次，排查「新容器怎么走错网」也要看两处。这两项作用于整个控制台而不是某个档案，「代理」页只留档案本身。
- **订阅链接**（「代理」页 → 新建/编辑代理 → 订阅链接）：贴机场或自建面板的地址，**保存时拉取一次**，解析出的节点缓存在档案里，之后用行内的「节点」挑一个、「刷新」重拉。四种响应形态都认：**base64 分享链接**（整份 base64 一个 blob，最常见的机场格式）、**明文链接列表**、**Clash YAML**（`proxies:` 列表，用仓库里已有的 `yaml` 依赖解析）与 **sing-box JSON**（整个配置或一个 outbounds 数组，`direct`/`selector`/`urltest` 这类路由决策会被丢掉，只取服务端节点）。分享链接覆盖 `ss://`（SIP002 与老式整串两种拼法、`?plugin=`）、`vmess://`（v2rayN 的缩写字段 `add/port/id/aid/scy/net/type/host/path/tls/sni/fp`）、`vless://`（含 reality 的 `pbk`/`sid`/`fp` 与 `flow`）、`trojan://`、`hysteria2://`/`hy2://`（含 `obfs=salamander`）、`tuic://`、`socks5://`、`http(s)://`；**`ssr://` 与不认识的协议跳过并在节点弹窗里列出原因**，一个怪节点不会毁掉整份订阅。**节点是缓存，不是每次现取**：起容器时绝不联网，所以断网机器照样能启动项目、机场掉线也不会让已经在跑的项目失去网络——刷新失败只把错误记在档案上、保留上一次的节点。生成的配置里**所有节点都在，路由走一个 `selector` 出站**，前面再加一个 **`urltest` 的 `auto` 组**（每 3 分钟用测速地址给节点排序，节点挂了自动漂走）；**换节点不需要重建容器**——项目侧换节点是给 sidecar 的 Clash API 发 `PUT /proxies/proxy`，立即生效、容器 id 不变（已建立的连接不迁移，只影响新连接）；档案级（「节点」弹窗里）的选择仍然只在下一次重建时生效，因为那改的是默认值；保存与刷新后都会用 `sing-box check` 校验一次，`sing-box` 不认的节点（比如 hysteria2 少了 TLS、reality 的 public key 不合法）会带着报错退回。`User-Agent` 可改：同一个地址按 UA 返回 base64 / Clash / sing-box 三种格式，默认 `sing-box/1.13.15`。**定时更新**可选 不自动 / 每 1 / 6 / 12 / 24 / 72 小时：服务端每 5 分钟查一次到期（`updatedAt + intervalHours`）的订阅并重拉，成功的换节点、失败的只把错误写进档案并保留上一次的节点，所以机场掉线不会让已经在跑的项目失去网络；后台刷新推的是 `push: true` 的配置，不会打断正在保存的表单。**批量测速**在节点弹窗里：一次起一个**临时 sing-box 容器**，把该订阅的全部节点做成出站，再用 Clash API 的 `GET /proxies/<tag>/delay?url=…` 让**每个节点真的去访问那个 URL** 并返回往返毫秒数（默认 `https://www.gstatic.com/generate_204`，可改成自己的地址；返回 204 的地址最准，因为它没有响应体）。这比连一下端口有意义得多——端口通不代表协议、密码和线路通——而一次容器就够整批节点用。临时容器不加入控制台的代理网络，API 只发布在宿主机回环上，测完即删；结果按节点存进 `proxies.json`，显示在节点右侧，可按时延排序，超时的排在最后。
- **WireGuard 档案**（「代理」页 → 新建代理 → WireGuard）：一条**隧道**而不是一个代理。**配置直接粘贴**（`wg0.conf`，机场与自建面板给的就是这个），粘贴后只做两处处理：`DNS =` 那行剥出来写成 `<配置目录>/proxy/<id>.resolv.conf`，以 `-v <文件>:/etc/resolv.conf:ro` 挂进作业容器（`wg-quick` 会拿它去调 `resolvconf`，镜像里没有这个命令；用挂载而不是 `--dns`，因为 Docker 不允许 `--dns` 与 `--network container:` 并用），`SaveConfig` 去掉（配置以只读方式挂进容器）。其余行原样保留——`PostUp`、多个 `[Peer]` 都不动，那是操作员自己的配置。加一个 **kill-switch 开关（默认开）**：隧道起来后删掉直连的默认路由，隧道掉了不会静默漏回宿主机网络。**为什么是独立 sidecar 而不是 sing-box 出站**：sing-box 的出站只能拨 TCP/UDP，ICMP 没有任何入口（实测作为出站时 ping 100% 丢包），所以"连 ping 都走隧道"必须用真网卡 + 真默认路由，也就是 `wg-quick`。实测：握手成功后 `ping 10.66.0.1`（对端）与 `ping 8.8.8.8`（互联网）都是 0% 丢包。sidecar 用的是**工具镜像** `sentinel:latest`（Dockerfile 里已加 `wireguard-tools` / `iproute2` / `iptables`），因此**必须先重建一次工具镜像**；它需要 `NET_ADMIN` 和 `--sysctl net.ipv4.conf.all.src_valid_mark=1`（wg-quick 的 kill-switch 会设这个 sysctl，容器里 `/proc/sys` 默认只读）。隧道只有一个出口，所以没有节点、没有 selector、没有自动择优，也不能运行时切节点——这和订阅档案是两种东西。
- **OpenVPN 档案**（「代理」页 → 新建代理 → OpenVPN）：第二条隧道，形态与 WireGuard 档案一致（真网卡 + 真默认路由、有 kill-switch、没有节点），区别在客户端是用户态的 `openvpn` 进程，所以 **sidecar 的主进程就是隧道本身**。**配置直接粘贴**（`.ovpn`，证书必须内联；`ca ca.crt` 这类外部文件引用会被拒绝并说明改法），账号密码**单独填**（写进 `<配置目录>/proxy/<id>.ovpn.auth`，0600，只挂 sidecar，不写进粘贴的配置文本），DNS 可留空——服务器 push 的解析器由 sidecar 的 hook 写下来、控制台读回去生成作业容器的 `resolv.conf`。粘贴的配置里这几类行会被剥掉：`daemon`（必须前台，否则 sidecar 一退出就带走作业容器的 netns）、`log` / `log-append` / `status`（日志要留在 `docker logs`，就绪与失败判定都读它）、`auth-user-pass`（改用挂载的凭据文件），以及 `up` / `down` / `route-up` / `tls-verify` 这些脚本钩子（它们指向镜像里没有的文件，而 sidecar 为了自己的 hook 必须开 `--script-security 2`，留着等于让粘贴的文件执行任意命令）。**就绪判定不能只看日志**：连上会打印 `Initialization Sequence Completed`，但**连不上时客户端会一直重试、容器始终 `running`**，所以控制台先看容器状态与致命行，再用 `docker exec <sidecar> ip -o addr show` 确认真有 tun 设备，60 秒等不到就把最后一行有意义的日志（`RESOLVE:`、`TLS Error:`、`AUTH_FAILED` 等）当错误抛给操作员——「容器在跑但没走隧道」这种静默泄漏因此不会发生。kill-switch 在 `--route-up` 里删掉直连的默认路由（OpenVPN 会为服务器地址留一条 /32 主机路由，隧道本身不断），实测断线期间路由全消失、`ping` 报 Network is unreachable，即失败时是「断网」而不是「漏流量」。**同一份证书同时只能有一个连接**：服务器没开 `duplicate-cn` 时两个项目共用一份档案会互相踢下线（实测每 60 秒一次 `ping-restart`、丢包从 0% 变成 50%~100%），所以代理页在隧道档案被两个以上项目使用时打「证书共用」警告——只警告不禁止，因为服务器开没开控制台问不到。工具镜像里加了 `openvpn` 与 `iputils-ping`（后者是为了能在作业容器里 `ping` 自证隧道通了），因此和 WireGuard 一样**必须先重建一次工具镜像**。
- **档案连通性测试**（「代理」页每行的「测试」）：普通代理、WireGuard、OpenVPN 档案都可以起一个一次性容器，用档案自己的出站或隧道真实访问一个可改的 URL（默认 `https://www.gstatic.com/generate_204`），测完即删。普通代理走节点测速同一套 sing-box + Clash API，隧道则先等 `wg0` / tun 就绪再从容器里 `curl`；结果（毫秒数或失败原因）按档案存进 `proxies.json`，行内显示，改档案保存时清空。订阅不在这一层测——节点弹窗里的「批量测速」逐个测，避免替操作员猜一个节点。隧道档案正被运行中的项目使用时，测试前会警告：同一份证书/密钥再连一次，可能让它们的隧道短暂中断（OpenVPN 未开 duplicate-cn 时会被踢下线）。
- **项目与档案的关系**：**项目只记住档案 id**，有三种选择——**跟随默认**（不存 id）、**不使用代理**（存 null）、**指定某个档案**；选了订阅档案之后还能**只给这个项目钉住其中一个节点**（`proxyNode` 存节点 tag，缺省表示跟随档案自己的选择）——同一个订阅常被多个项目共用，但一个打外网、一个走另一个出口是常见需求。钉住的节点在订阅刷新后如果没了，会**回落到档案自己的选择**而不是让配置生成失败（节点 tag 是身份，改名等于换节点）。改一次档案或节点、用到它的项目下次重建容器就生效，而删除档案时用它的项目回到「跟随默认」而不是留下悬空引用。新建项目可以在创建表单里直接选档案与节点，侧栏项目选择器的每一行也能就地展开档案、再展开它的节点。开启代理的项目容器不再用 host / bridge 网络，而是**挂到该项目自己的 sing-box sidecar**（`--network container:<sidecar>`），容器里的一切出站（nmap、curl、反弹 shell 的外连）都进隧道。控制台负责必须对的部分：tun 入口（地址取 `198.18.0.1/30`，不落在任何 Docker 网段里，避免遮住 sidecar 自己连代理的默认路由）、域名解析走 Docker 内嵌 DNS 而 `protocol: dns` 与 `ip_is_private` 直连（前者是必需的：把 `127.0.0.11` 的查询送进远端出口会让所有域名解析不了）、`strict_route` 保持关闭。**节点凭据不进作业容器**：生成的 `config.json` 按项目 id 写在 `<配置目录>/proxy/<id>.json`（0600），只以 `:ro` 挂进 sidecar，Agent 在 Kali 容器里读不到——这也是选 sidecar 而不是把 sing-box 跑进作业容器的主要原因；代价是容器不再有 host 网络的入站能力（目标连不回反弹 shell、`127.0.0.1` 不再是宿主机），需要时把该项目设成「不使用代理」。**切换节点的管理面**：生成的配置里带 `experimental.clash_api`，端口在 `127.0.0.1` 上由 Docker 临时分配（`-p 127.0.0.1::PORT`，切换时才用 `docker port` 问一次，所以不存在端口撞车），secret 每个项目随机生成、只写在生成给 sidecar 的配置里（0600，只挂 sidecar，作业容器读不到）。**作业容器共享 sidecar 的 netns，所以它也能连到这个端口**——secret 是唯一的锁，无 secret 是 401；一旦泄露，容器能读 `/connections`（它在连谁）并切换/切断连接，这是开这个管理面的代价，不切节点时它完全不被使用。

**sidecar 与容器必须按顺序成对管理**：创建时先起 sidecar 再创建容器，停止时先停容器再停 sidecar（Docker 不允许挂到没运行的 netns 上），并且**永远不要单独重启 sidecar**——它的重启会换掉 netns，正在运行的容器会保持 `Up` 却连 eth0 都没有，之后所有命令都以莫名其妙的方式失败。环境页的「项目容器」检查项用两条判据识别这种失效（`HostConfig.NetworkMode` 指向的容器 id 是否还是当前的 sidecar、sidecar 的 `StartedAt` 是否晚于容器），发现后下次使用该项目时重建容器（`/work` 不受影响）；只是改了档案、容器还活着的情况只报告不重建，环境页提示去点「重建容器」。`--add-host` 不能和 container 网络模式并用，所以 `host.docker.internal`（frida 隧道用）改由 Docker 内嵌 DNS 解析，Linux 引擎上由控制台在每次启动后补写容器 `/etc/hosts`（Docker 每次 start 都会重写该文件）。sidecar 加入的是一张控制台自建的 user-defined 网络（`sentinel-proxy`），内嵌 DNS 因此在同一个 netns 里，Docker Desktop 也顺带解析 `host.docker.internal`；tun 设备节点在容器内 `mknod` 生成，不依赖宿主机有没有 `/dev/net/tun`。档案、订阅地址与镜像名存在 `<配置目录>/proxies.json`（0600，含账号密码与订阅 token），与「容器网络」同一套语义：保存只影响之后新建或重建的容器（容器层会丢，`/work` 不丢）
- **重建容器**（项目页每行的「重建容器」）：Docker 不允许改已有容器的网络模式与能力，所以改完「容器网络」这类创建期设置后，已有项目要点它才会套用。重建只换容器：项目 id、名称与工作目录（`/work`）不变，容器里 apt 装的包与 `/work` 之外的文件会丢，重建期间正在跑的命令会失败。开了代理的项目重建时会连 sidecar 一起换（顺序是删容器 → 删 sidecar → 起 sidecar → 起容器）
- **构建镜像**：镜像不存在时在环境页直接点「构建镜像」构建 `sentinel:latest`（二次确认，构建输出实时滚动，可「中止构建」）。仓库里运行时用 `docker/` 目录作构建上下文；单文件二进制运行时把内嵌的 Dockerfile 写到临时目录再构建，因此不需要带任何文件
- **Docker 门禁**：只要有阻断项没通过，控制台就拒绝 `prompt`、`compact` 和子代理 steer（服务端返回失败原因），所有页面顶部显示红色横幅，输入框锁定为「已锁定」并显示原因——与其让命令在容器里失败，不如先让人把环境修好。未选项目时引导页只替换对话页，设置页与项目页仍然可达，否则首次使用就没法进环境页构建镜像
- **POC 订阅**（设置页「POC 订阅」）：订阅远程 zip 模板包。源 = 名称 + zip 直链 + 可选认证头 + 可选自动间隔（默认 24h）；手动「立即同步」或定时拉取，走与手动导入相同的去重覆盖路径，只增不减（同步从不删除本地模板）；下载限 512MB / 10 分钟 / 重试一次，每个源保留最近 5 次同步记录，失败可推钉钉（通知 kinds 新子项「POC 订阅失败」）。页头与 POC 库页头各有「一键同步官方 POC」：源不存在时自动创建官方 `projectdiscovery/nuclei-templates` 源（id `official`，仅手动）并同步，已存在则同步它当前的 URL（改成镜像再点即可），重复点击不会堆出重复源
- **POC 库**（侧栏「工作台 → POC 库」）：操作员导入的 Nuclei 模板中心，全局共享（`~/.sentinel/agent/pocs.db`，不进容器）。导入支持多选 yaml 与 zip，按模板 `info.id` 去重覆盖（顶层带 `workflows:` 的 nuclei workflow 不是模板，跳过并单独说明原因）；Agent 只有 `poc_search` / `poc_read` 两个只读工具（「设置 → 权限」的 `poc_read` 开关控制，旧配置按关闭读取），`poc_search` 一次最多列 100 条元数据并明确提示「还有更多」，`poc_read` 一次可取多条模板全文（最多 8 条），模板文件永不挂进项目容器——要实际执行，Agent 必须自己写 yaml 到工作目录再用 bash 跑 nuclei
- **群通知（钉钉 / 飞书 / 企业微信）**（设置页「通知」）：一次运行结束（完成 / 失败 / 已中止）后向群机器人推送 markdown 消息（钉钉、飞书、企业微信可同时启用），含状态、项目、会话状态、耗时、token 用量与花费、最后回复（默认截断 2000 字，可在设置页改成任意字数，`0` 表示不截断）与失败原因。支持「加签」（secret 留空则不加签）与「自定义关键词」；字数上限同时作用于任务报告的「最后回复」、持续目标的「结论」和漏洞通知的「原始数据包」，超出钉钉单条 20000 字节（飞书 30000、企业微信 4096）时按字节硬截断并注明；「发送测试消息」可先验证机器人；企业微信机器人只有 webhook 一种配置（平台无加签/关键词），`###` 标题会转为加粗行渲染。输入框旁的「通知」开关按条决定本次运行是否推送，默认跟随全局开关，全局关闭时也可单条强制发送；发送失败重试 2 次，最近一次发送结果显示在设置页
- **资产测绘平台**（设置页「资产测绘」）：接入 **FOFA**、**360 Quake**、**奇安信 Hunter** 三家互联网资产测绘平台，用操作员自己的账号查询公网已测绘到的资产。**三家各一个工具**（`fofa_search` / `quake_search` / `hunter_search`），因为三家查询语法不通用——FOFA 写 `ip="1.1.1.1"`、Quake 写 `ip:"1.1.1.1"`、Hunter 写 `ip="1.1.1.1"` 但字段名与分页参数各不相同；合成一个工具就得猜方言，猜错的代价是「查不到」而不是报错。工具说明里写明各自语法与申请地址。**挂载规则**：只有「已启用 + 已配置密钥 + 已验证通过」三个条件同时满足的平台才把工具挂给 Agent（`asset_read` 开关另在「设置 → 权限」里，旧配置按关闭读取）；未配置或密钥不可用的平台**根本不挂载**，Agent 看不到该工具，而不是拿到一个每次调用都失败的工具。三家都支持**自定义 BaseURL**（可填反向代理前缀，如 `https://proxy.example/fofa`，留空使用官方地址；控制台自动拼接各平台 API 路径）。保存时会按新地址自动验证一次，也可以单独点「测试连接」（验证结果立即生效，会按需重建会话）；页面上显示每个平台最近一次调用结果与剩余额度。**查询由控制台进程直接发出**，密钥不进容器、不进 bash 命令、不进守门审计；每次查询记一条流水到 `<配置目录>/assets.db`（含查询语句、平台、条数、耗时、错误、额度、来源会话与证据路径），原始响应写入项目工作目录的 `evidence/asset/`（按时间命名，报告里可直接引用）。密钥明文存在 `<配置目录>/assets.json`（0600），前端不回显（留空表示不修改，另有「清除已保存的密钥」）。三家都按次计费，另有「每个会话查询次数上限」（按会话三家合计、子代理共用，`0` = 不限）。删除项目连带删除该项目的查询流水。**查询内容与密钥会发送给这三家第三方平台**，见「安全提示」

apk_search` 挂进**该对话**的 Agent 提示词（默认不挂，Web 渗透会话零痕迹；一个对话打开不会影响其他对话）。开关状态作为会话条目 `zg-droid` 随对话保存，刷新、重开或 fork 后保持。**安卓 shell 命令走与 bash 完全相同的守门/审批链**（审批卡片显示「设备「X」」，判定入 `gatekeeper.db` 审计）；frida、抓包与 APK HTTP、DNS）。动态调试走 **TCP-over-WS 隧道**：`droid_frida_setup` 推送并启动 frida-server（二进制需先放 `/work/frida-server`，版本与容器内 frida 匹配），网关在本机起回环监听桥接进设备 127.0.0.1:27042，容器内 frida-cli 经 `host.docker.internal` 直连；`droid_frida_ps / droid_frida` 支持 attach/spawn 与内置脚本（okhttp 明文日志、SSL pinning bypass、root 检测绕过、crypto 日志）或 `/work` 自定义脚本，限时运行回收输出。静态分析：APK 传 `/work` 后 `apk_decompile`（jadx+apktool 反编译到 `/work/decompiled/<名>/`）→ `apk_manifest`（包名/权限/导出组件/debuggable/backup/cleartext/深链清单）→ `apk_search`（源码/资源内正则检索硬编码密钥与端点）。**抓包证据库**：操作员本机 Burp/HAR 导出或原始请求文本用 `capture_import` 导入（按项目存 `captures.db`），`capture_search / capture_get` 检索引用，`capture_replay` 生成重放 curl（替换他人 Cookie/Token 即可做越权对比，运行仍过 bash 审批链）。挖到的客户端/服务端漏洞照常走 `vuln_submit` 进漏洞中枢，`platform: android` SIGSTOP：所有线程停住、TCP 仍是 ESTABLISHED，控制台只看到一个「在线但什么都不回」的设备，而冻住的进程自己发不出 SIGCONT，第二个进程是唯一不需要 root、不需要 adb 的「外部」——同 uid，内核允许它给兄弟进程发信号。救不了「整个包一起被冻」（那时它同样被冻住，只能靠设备外的看门狗或关掉模拟器的后台冻结）。设置页可关（默认开，代价是第二个前台通知，渠道重要度 MIN、默认折叠）；点「停止反连」时两个进程一起停，不会把主动停掉的服务又拉起来。APK 构建：`scripts/build-droid-apk.sh`（Gradle 与 Android SDK 均走腾讯镜像，AGP/依赖走阿里云镜像）
- **业务建模**（输入框上方「业务建模」按钮，成果在侧栏「工作台 → 业务建模」）：Agent 在**当前会话**里把目标的接口还原成一份 OpenAPI 3.0 文档，并整理出它背后的业务实体与关系。**工具一直在工具表里，但只在操作员要它建模时才该调用**：`api_model_submit` / `api_model_done` 在控制台会话里默认启用（工程任务的 worker 与子代理都不挂），所以操作员也可以直接在对话里说「帮我做业务建模」——模型第一次 `api_model_submit` 会自己开一次建模并落库。两个工具的说明与提示词准则都以「只在操作员要求业务建模时调用；用户不需要业务建模时不要调用这个工具」开头，避免它在普通渗透工作里自作主张；`api_model_done` 在没有进行中的建模时仍然拒绝。输入框上方的「业务建模」按钮是另一条入口，点击不弹窗：直接把一段建模简报作为一条可折叠的「业务建模已启动」标记行注入会话并开始跑，模型、权限、命令门都沿用当前会话（目标以会话里已经确认的为准，不明确时它会先问一句）。`api_model_submit` 可反复调用：整份 `openapi` 覆盖草稿，或 `paths` / `components` 分片按 key 合并进草稿（接口多的站点分批交，中途被截断也不会丢掉已确认的部分），同一个调用里可用 `entities` 交业务实体（`name` 必填，可带 `fields` / `relations`）；服务端校验合并后的文档（必须 3.x、必须有 `info.title` / `info.version` 与 `paths`、单份 ≤512KB、路径 ≤5000），被拒绝时按返回的具体原因改，实体的问题只作为提醒、不影响端点入库。`api_model_done` 由 Agent 自己声明完成（要写清覆盖范围），操作员也可在同一个按钮上手动结束（会话运行中不允许，先中止）。记录落在 `<配置目录>/apimodels.db`（SQLite，不进容器），页面只读，详情页不整页滚动：元信息收成页头下的一条信息条，下面是「接口文档 / 业务实体 / 时间线」三个标签页，各自滚动——文档页签用**内嵌 Swagger UI** 直接阅读（`swagger-ui-dist` 打进前端资源，占满剩余高度，文档内联进沙箱 iframe，不发起任何对目标的请求——「Try it out」已移除），另有导出 JSON / YAML、跳回发起它的会话；**每次建模是一条新记录**，重做不覆盖上一次，删除项目连带删除该项目的全部记录，会话已经不在了也可以在页面上「标记已结束」
- **手动压缩上下文**：把当前会话压缩成摘要后继续（对话页工具栏「压缩上下文」按钮，或直接输入 `/compact`）；上下文超限报错时提示该操作。压缩期间工具栏显示「压缩中 N 秒」和「中止压缩」，输入框与目标对话框锁定并给出中文原因，点「中止压缩」即放弃这次压缩（不会留下报错），会话立刻可以继续。**压缩不会让上面的对话消失**：会话记录始终是整条分支，压缩处插入一行可展开的「会话摘要（压缩）· 压缩前 N tokens」标记，多次压缩逐层保留，模型看到的是摘要，操作员看到的仍是完整审计轨迹
- **思考等级**：按模型能力列出可用等级（关闭 / 最低 / 低 / 中 / 高 / 极高 / 最大），在对话页工具栏即时切换，只对当前会话生效
- **复读保护（loop-guard）**：模型陷入复读（同一行或同一小段内容连续重复，常见于压缩上下文之后）时，扩展在检测到重复的那一刻中止这次请求，把重复的尾部从消息里截掉（重复文本留在上下文里只会诱发下一轮复读），并以一条可折叠的「输出重复已中止」提示自动续跑，要求它换一种方式继续；同一个 prompt 连续 3 次复读后不再自动续跑，交给操作员处理。另外按会话统计「同工具 + 同参数」的连续调用，在第 3 / 5 / 8 次注入一条「重复工具调用提醒」（只提示，不中止）。两类提示都是 `custom_message` 条目（`customType` 为 `zg-loop-guard`），模型收到的是 user 消息，控制台里折叠成一条提示行而不是操作员的输入
- **图片输入**：粘贴截图或选择图片文件随消息发送，会话记录中保留缩略图。注意 pi 只会把图片发给声明了 image 能力的模型，本控制台写入的端点配置默认声明 `input: ["text","image"]`；纯文本端点请在 `models.json` 中改回 `["text"]`
- **文件上传**：拖拽或粘贴任意文件到输入框，或点输入框上方的「附件」按钮选文件（「图片」按钮仍只收图片），每个文件一个 chip（名称、大小、上传进度、可删除），上传完不自动发送——按 Enter 才随消息发出。文件写进当前项目工作目录的 `uploads/`（重名自动加 `-2`/`-3`，不覆盖已有文件），发送时在消息正文前拼一段清单「已上传文件（可用 read/bash 直接读）：- `<绝对路径>`（大小）」，模型用自己的 read/bash 去读——消息本身只多这段文本，协议不变（模型消息只支持 text 与 image 两种 part，非图片文件只能落盘给路径）。传输走 `POST /api/upload?name=…`（body 是原始字节，XHR 上报进度），服务端边收边写盘、单文件上限 1024MB、文件名净化成单段（`../../evil.sh` → `uploads/evil.sh`、`/etc/passwd` → `uploads/passwd`），超限或中断会删掉半成品并回 413/400 + 中文原因，没选项目回 409。图片仍走上面那条 vision 路径、不落盘；上传后切换了项目再发送会被拦下并提示重新上传（旧项目目录没挂进容器，那个路径模型读不到）。宿主会话与容器会话都能用：文件写在挂载的宿主侧，容器里的 `/work/uploads/…` 与宿主绝对路径是同一个 inode
- **内置扩展**：codemode（沙箱内脚本批量调工具）、tool_search 与 loop-guard（复读保护）默认启用；MCP 服务器在「设置 → MCP」里维护，存 `~/.sentinel/agent/mcp-servers.json`，会话启动时连接
- 会话管理：会话挂在侧边栏「对话」下（悬停显示重命名 / 删除）、切换、新建（JSONL 会话文件即审计日志）
- 会话记录按控制台日志呈现：操作者输入是一行命令回显，代理输出是正文段落。一次运行的过程（思考、工具调用、中间说明）挂在正文左边缘的一条竖轨上，每次调用是轨上一个圆点：运行中蓝色、完成绿色、失败红色，行内显示工具名、命令或最新一行输出、以及结果与耗时；点开某一行才变成深色终端块（命令、完整输出、复制、全屏）。**运行一结束，整段过程自动折成一行「过程 · N 次工具调用 · N 段思考 · 耗时」，正文只留你的指令和最后的总结**，点开可完整回看；失败、中止和正在跑的运行不折叠，错误一定看得见；压缩后保留的那一段前面已经没有指令了，同样折成「过程」行。输出顺序由事件流决定：运行期间消息按到达顺序渲染，运行结束的 snapshot 再统一接管，不会出现文字消失或工具卡片堆到最后（刷新才恢复）
- **单文件二进制**：`scripts/build-web-binaries.sh` 用 `bun build --compile` 把服务端、前端资源、Dockerfile 和 coding-agent 的包信息打进一个可执行文件（darwin-arm64 / darwin-x64 / linux-x64 / linux-arm64 / windows-x64），目标机器上不需要 Node、npm 或 node_modules，只需要一个 Docker 守护进程；Windows 版需要 Docker Desktop
- 模型端点配置：OpenAI 兼容端点（vLLM / one-api / new-api 等）。模型库（名称、地址、角色指向）写在 `~/.sentinel/agent/model-library.json`，SDK 读的 provider 注册表 `~/.sentinel/agent/models.json` 由它同步生成，一条模型一个 provider。**主模型的改动在下次发送时生效**（不打断正在跑的会话），守门模型与漏洞评审改完立即生效

## 架构

```
浏览器（React，中文界面）
   │  WebSocket /ws（JSON 协议，见 src/protocol.ts）+ 静态资源 HTTP
server.ts（node:http + ws）
   │  直接调用 SDK
sentinel-session.ts —— createAgentSession() + baseToolsOverride(bash 包装审批门 / 守门员)
   │        │
   │        ├── files.ts / subagent-store.ts / vulnerabilities.ts
   │        │   （docker exec 文件操作、子代理记录、漏洞中枢 SQLite）
   │        └── gatekeeper.ts + gatekeeper-store.ts + gatekeeper-config.ts
   │            （判定调用、判定流水 SQLite、全局默认模式与超时/并发配置）
   │
pi coding-agent（AgentSession / SessionManager / 工具 / 压缩 / 会话树）
```

bash 工具通过 `BashOperations.exec` 包装实现拦截，三种模式在同一个包装里分派：审批模式下命令先广播到所有已连接的控制台，等待操作员决定（批准 / 编辑后批准 / 拒绝），中止运行会取消未决审批；自动执行直接放行；AI 审批把命令交给守门员模型，`ALLOW` 放行、`BLOCK` 以理由回绝、判定失败放行并记录。模式按会话解析（本会话覆盖 → 全局默认），所以包装拿到的是一个 `() => SentinelMode` 闭包而不是启动时的固定值。

守门员的判定记录写在配置目录的 `gatekeeper.db`（`~/.sentinel/agent/gatekeeper.db`），与漏洞中枢同样的理由：不进容器。每条记录含来源、命令、判定、理由、耗时、模型来源与 tokens，`ALLOW` 也入库；判定失败同样入库（`failed`），因此「守门员掉线期间放行了什么」可以事后核对。

文件面板与子代理面板不经过审批门，但都限制在项目容器内：文件操作把路径归一化到 `/work` 之下并以位置参数传给容器脚本（不做字符串拼接），子代理只能由主代理派生且同样使用被包装的 bash。

漏洞中枢的数据库在配置目录（`~/.sentinel/agent/vulnerabilities.db`），不在项目工作目录里：工作目录挂进容器，容器内的一条 `rm` 或 `sqlite3` 就能改掉或抹掉记录。代理提交时项目按「会话创建时」绑定，而不是读当前页面上的项目——切换项目后旧会话仍可能在后台跑，它提交的记录必须留在它发现漏洞的那个项目里。

持续目标由 `src/goal.ts`（纯状态机：轮次、熔断、完成/阻塞判定）、`src/goal-tool.ts`（`goal_progress` / `goal_complete` / `goal_blocked`）与 `sentinel-session.ts` 里的驱动组成。驱动挂在会话的 `agent_settled` 事件上：结算本轮、判断是否续跑、注入下一条合约。合约与状态都用会话条目写入会话文件——合约是 `custom_message`（会话记录里一行可折叠的「目标续跑」，模型收到的是 user 消息），状态是 `custom` 状态条目（不进模型上下文）。因此分叉、压缩、重启都不会丢目标，续跑也不会污染操作员消息构成的分叉点。完成声明里的「已提交 N 条」与运行时实际计数硬校验：运行时只统计本目标开始后经 `vuln_submit` 入库的记录（含子代理提交），少报多报都会被拒绝。

业务建模由 `src/modeling.ts`（简报文本、`zg-modeling-state` 状态条目、工具装载规则）、`src/apimodel-tool.ts`（`api_model_submit` / `api_model_done`）与 `src/apimodels.ts`（文档、实体、审计流水与导出）组成，驱动在 `sentinel-session.ts`。装载规则就是 `modelingToolLoadout(active, modeling)` 这一个函数：两个工具以 `defaultActive: false` 注册，所以任何会话初始的工具表与系统提示词里都没有它们；点按钮时用 `setActiveToolsByName` 把两个名字加进去（SDK 在下一回合重建系统提示词），结束时再减掉。运行状态写成会话条目（`custom`，不进模型上下文），所以重启、因权限变更重建会话、分叉都会把「还在建模」这件事一起带走，重建后按同一条规则还原工具表。文档存在配置目录的 `apimodels.db`：工作目录挂进容器，容器里的一条 `rm` 就能带走成果。

资产测绘由 `src/asset-config.ts`（`assets.json` 读写与「可用」判定、自定义 BaseURL 归一化）、`src/asset-platforms.ts`（三家 HTTP 客户端、自定义 BaseURL 拼接、两种 base64 编码、错误归一、账号额度探测、按平台串行队列与限流退避）、`src/asset-store.ts`（查询流水 SQLite）与 `src/asset-tool.ts`（三个工具与证据落盘）组成，驱动在 `sentinel-session.ts`。工具在**会话创建时**按可用平台集合生成，所以保存配置会重建活动会话（与权限页同一条规则，有会话在跑时拒绝保存）。三家客户端对同一平台串行：Quake 对并发请求直接返回 `q3005`（调用 API 过于频繁），退避重试后才算失败；FOFA 的 `qbase64` 用标准 base64，Hunter 的 `search` 用去掉 padding 的 base64url，两者不能共用一个编码器。密钥在每次调用时才从配置读取（不缓存在工具闭包里），因此操作员换密钥不需要重建会话。

自定义 MCP 服务器由 `src/mcp-config.ts`（`mcp-servers.json` 读写、`loadConfig` / `updateConfig`、挂载判定）与 `src/components/McpPanel.tsx` 组成，驱动在 `sentinel-session.ts`；连接探测复用 coding-agent 导出的 `probeMcpServer()`，它内部就是会话用的那个 `McpServerConnection`，所以「测试连接」看到的结果与 Agent 实际拿到的工具一致。`createMcpExtension` 在会话创建时被传入自定义 `loadConfig`，工具集合因此在**会话创建时**确定，保存配置要重建活动会话（与权限页、资产测绘同一条规则）。

## 使用

在仓库根目录：

```bash
npm install --ignore-scripts
npm run build          # 构建所有包（包括本包）
npm --prefix packages/web run start
```

打开启动日志里打印的入口地址（形如 `http://127.0.0.1:7777/K7nD1LGJfYFN`）即可使用。

控制台默认监听 `0.0.0.0`，服务器上直接启动就能从外部访问（只想本机访问传 `--host 127.0.0.1`）。为避免被 FOFA 这类引擎扫到并收录，启动时会生成一个随机入口串：只有打开入口地址（会给浏览器种一个 cookie 再跳回 `/`）才能看到控制台，其余任何请求一律返回一个普通的 404。入口串每次启动都会变，需要固定用 `--gate-token`（或环境变量 `SENTINEL_GATE_TOKEN`），不要这层用 `--no-gate`；密码登录照旧生效。

### 单文件二进制

```bash

./scripts/build-web-binaries.sh --platform linux-x64    # 只构建一个平台
./scripts/build-web-binaries.sh --platform linux-arm64  # Linux arm64
./scripts/build-web-binaries.sh --platform darwin-x64   # Intel macOS
./scripts/build-web-binaries.sh --platform windows-x64  # Windows：sentinel-web.exe + zip（含 replayd/）
./scripts/build-web-binaries.sh --skip-build            # 复用已有 dist
```

产物在 `packages/web/binaries/`。Unix 平台是 `sentinel-web-<平台>.tar.gz`，解压后是 `sentinel-web/` 目录（可执行文件 + 容器用的 `replayd/`）；Windows 本地同样产出 `windows-x64/sentinel-web.exe`（zip 的内容，也是冒烟测试跑的那个），但**发布出去的资产只有 `sentinel-web-windows-x64.zip`**（exe + `replayd/`），跟另外四个平台一样一个平台一个归档：

```bash
./sentinel-web --check          # 只跑 Docker 环境检查，未通过时退出码 1
./sentinel-web --port 7777      # 启动控制台
```

`replayd/` 里是发包重放服务的 Linux 二进制（amd64/arm64），控制台首次在项目容器里用到「发包」时把它下发进容器（见 `src/replayd.ts`），因此必须放在可执行文件旁边；不放也能跑，只是发包工具会明确报告找不到二进制（可用 `SENTINEL_REPLAYD_DIR` 指向别处）。构建脚本需要 Go 与 pnpm/npm 来产出它，缺工具链时跳过并给出提示，`SENTINEL_SKIP_REPLAYD=1` 可显式跳过。

二进制里带着前端资源和 Dockerfile，所以**除了 `replayd/` 之外**旁边不需要任何文件；运行时把 coding-agent 的 `package.json`、README、CHANGELOG 和 docs 解包到系统临时目录（`$TMPDIR/sentinel-web-package`）并指向它，否则 pi 会退回自己的默认值，把状态写进 `~/.pi/agent`。它仍然需要目标机器上有 Docker 守护进程和 `sentinel:latest` 镜像（环境页可以直接构建）；linux-x64 产物链接 glibc，Alpine 等 musl 发行版需要额外兼容层。

首次使用先在侧栏「设置 → 模型」添加一条模型（或在 `~/.sentinel/agent/models.json` 手动配置端点），确认「主模型」角色选中了它，在「设置 → 环境」确认 Docker 与 `sentinel:latest` 镜像可用（缺失时可直接构建），然后新建一个项目：控制台没有默认目录，未选择项目时只能看到创建项目的引导页。

```json
{
	"providers": {
		"zg-endpoint": {
			"baseUrl": "http://127.0.0.1:8000/v1",
			"api": "openai-completions",
			"apiKey": "sk-…",
			"models": [{ "id": "deepseek-v3.1" }]
		}
	}
}
```

## 安全提示

- 审批模式只拦截 bash 工具；read/edit/write 不拦截。AI 审批同样只判 bash。
- **AI 审批不是沙箱，也不做数据防泄漏**：守门员只拦「会破坏目标可用性、业务数据完整性或系统配置」的六类操作，读敏感文件、上传 webshell、爆破口令都按授权渗透的正常手段放行。判定失败、超时、回复无法解析一律放行（fail-open），因此守门员掉线时等价于自动执行——审计页的「请求失败」计数与顶部黄条就是用来发现这种状态的。判定依赖模型对单条命令的理解，绕过方式（把破坏性操作藏进脚本、编码后执行、经由 MCP 工具或 codemode 间接执行）它看不出来：`code` 工具在沙箱内调用 bash 仍会被判定，但 MCP 工具、文件面板、read/edit/write 都不过门。
- **文件面板不经过审批门**：它以容器 root 身份上传、覆盖、重命名和递归删除 `/work` 内的文件，`/work` 之外与工作目录根节点本身会被拒绝。路径按文本归一化（`..` 会被折叠后校验），但**不解析符号链接**：容器内指向 `/work` 之外的软链接仍会被跟随。能改容器内文件的操作员本来就持有容器 root，因此这里只做边界保护，不做权限隔离。
- **MCP 工具与 codemode 不经过审批门**：它们不是 bash，`code` 工具在沙箱内调用工具时仍走被包装的 bash，但 MCP 服务器暴露的工具会直接执行。启用 MCP 前请确认服务器来源可信。
- **MCP 的 stdio 服务器是宿主机子进程**：它不在容器内执行，也不受容器边界约束，能起什么进程取决于「设置 → MCP」里配置的命令。所以 stdio 条目必须勾选宿主机执行确认才能保存，控制台自己也不读 pi 的 `mcp.json`——列表里没有的服务器，Agent 就没有。
- **路径只有两个名字，指的是同一份数据**：项目目录在容器里同时挂在 `/work` 和它的宿主绝对路径上（同一 inode），bash 用哪种写法都写进共享卷；容器自己的 `/tmp` 与宿主机 `/tmp` 无关，read/write/edit 看不到，只能作为容器内的临时中转。系统提示词给模型的是宿主路径，所以同路径挂载是必要的——否则用宿主路径写文件会落进容器可写层，宿主机和文件面板都看不到，容器一重建就丢。老容器（在本次改动前创建的）没有这条挂载，环境页会给出「工作目录挂载」警告，重建前先用 `docker cp` 把容器内该路径下的文件捞出来
- **`read/edit/write` 不受容器约束**：它们以控制台用户身份直接读写宿主机文件系统，项目目录只是相对路径的基准，**绝对路径不受限制**（被限制在容器 `/work` 之下的只有文件面板）。
- 控制台会加载项目工作目录下的 `settings.json`、`.pi/extensions` 与 `AGENTS.md`。与 CLI 不同，这里没有项目信任确认步骤：不要把这些文件来自不可信来源的工作目录设为项目。MCP 服务器不在此列：它们只来自「设置 → MCP」，项目目录里的 `.pi/mcp.json` 与配置目录里的 `mcp.json` 都不读。
- **漏洞中枢只有代理能写、只有操作员能改**：`vuln_submit` 是唯一的写入入口，提交内容逐字入库；状态、等级、CVSS 与备注只能从控制台改，改动进时间线。因此「模型认为的」和「人复核过的」始终分得开。提交不经过审批门（它不改目标、不执行命令），要拦住它请在「设置 → 权限」里关掉 `vuln_submit`；`vuln_read` 只放开查询。旧配置文件里这两个开关不存在时按关闭处理
- 自动执行模式下模型可运行任意命令。pi 无内建沙箱，请仅在授权目标与隔离环境中开启自动执行，必要时配合容器化运行；需要无人值守又不想全放行时用 AI 审批。
- **发包重放走 `docker exec` 桥接，不发布端口**：`replayd` 只监听容器内回环 `127.0.0.1`（端口按容器名推导，被占用时顺延重试），控制台通过容器内 `curl` 调它的 REST，所以不发布端口、不改容器创建参数，host 与 bridge 两种网络模式都可用，已有容器也不必重建。访问 token 由 replayd 自己生成在挂载的数据目录 `token` 文件（0600）里，由容器内 `cat` 读取，不进入 `docker exec` 的命令行参数、不进控制台内存。**它真的会打到目标**：`replay_capture` 与 bash 同级过审批链，审批卡片上显示的是完整报文（可编辑后放行）；`replay_flows` 只读本容器历史。截图依赖容器镜像里的 Chromium（`docker/Dockerfile` 已装 `chromium` 与 `fonts-noto-cjk`，中文字面不会变方块）：镜像没装浏览器时截图会明确报错并给出补装方式，**不会**偷偷去公网下载浏览器。数据目录在项目工作目录内，容器里的命令与文件面板都能读写它
- **文件夹打包会读取整个 /work 子树**：打包在容器内以 root 执行，`/work` 里 Agent 能读的文件都会进入压缩包；符号链接不跟随，但隐藏文件与点目录包含。压缩包临时落在控制台本机 `downloads/`，下载完成或 10 分钟后删除；不设大小上限，超大目录可能长时间占用 CPU 与临时磁盘。下载路由与 `/api` 其他接口一样要求登录态与控制台承诺。
- **资产库只写本机**：`asset_report` / `asset_note` 只把数据写进控制台的 `asset-library.db`，不发起网络请求，也不经过 bash 审批或容器；资产数与记录数不设上限。导出的 Markdown 与页面会包含内部域名、IP、URL query（可能是令牌）与测试备注，按敏感材料处理。旧 `permissions.json` 没有 `asset_library_write` / `asset_library_read` 两个键时按关闭处理，需在「设置 → 权限」打开
- **资产测绘会把查询内容与 API Key 发送给第三方平台**：查询由控制台进程直接 HTTPS 发出，不过审批门、也不经过容器，但目标域名、IP、标题等查询内容对 FOFA / 360 Quake / 奇安信 Hunter 可见，且会占用操作员账号的额度。密钥明文存在 `<配置目录>/assets.json`（0600），前端不回显、不进 bash 审计、不进守门员判定，但它是操作员账号的凭据，泄露即等于额度被用。配置自定义 BaseURL 时，密钥与查询内容会发送到该地址，只应填写可信的反向代理。查询流水（`assets.db`）与原始响应（项目 `evidence/asset/`）留在本机；证据文件在项目工作目录内，容器里的命令同样能读写它。只挂载「已验证通过」的平台是为了避免 Agent 反复调用一个不可用的工具，**不是**访问控制：`asset_read` 关掉即整体摘除工具，但它只控制工具是否挂载，不控制操作员自己在页面上测试连接。
- **持续目标在自动执行下没有危险命令黑名单**：目标模式可在自动执行或 AI 审批下运行，自动执行时运行期间是全放行的（目标条上固定显示「自动模式 · 全放行」）。控制台只做轮数上限、连续空转、同一阻塞三重熔断，不会拦截 `rm -rf` 之类的命令，也不会在续跑时重新征求确认。请只在授权目标上启动持续目标；要边跑边兜底就选 AI 审批。
- **容器代理让出站流量经过第三方，并放弃容器的入站能力**：开了代理的项目，Kali 容器共享 sing-box sidecar 的网络命名空间，里面发出的一切（含扫描器流量、DNS 之外的出站、反弹 shell 的外连）都从操作员配置的代理出去——流量内容与目标地址对代理运营方可见，节点凭据也由它保管，只应使用自己信任的出口。**节点配置不进作业容器**：生成的 `config.json` 存在配置目录（0600，删项目时一并删除），只以只读方式挂进 sidecar，Agent 在容器里读不到它；但共享 netns 意味着 `127.0.0.1` 与 sidecar 共用，因此不要把 sing-box 的管理接口（如 `clash_api`）开在回环上——容器里的 root 能连到它，也就能读到节点信息。代理模式下容器不再有 host 网络的入站能力（目标连不回反向 shell、`127.0.0.1` 不再是宿主机），要保留就对该项目选「不使用代理」；`ip_is_private` 直连（默认开）只保证内网目标可直连，不改变入站。**sidecar 不要单独重启**：重启会换掉 netns，正在运行的容器仍显示 `Up` 却已失去全部网卡，只有重建容器才能恢复。
