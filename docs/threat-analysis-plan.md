# 威胁反制：架构与实现说明

入口为“情报 → 威胁反制”。按工程指挥思路分析设备上报的威胁 IP 与告警证据，生成关联分析及防御建议。设备接入协议和默认值见 [接入指南](threat-intelligence.md)。

## 业务规则

| 项目 | 实际行为 |
| --- | --- |
| 接入 | 统一 JSON 主动推送，设备转换格式；每数据源独立 Token |
| 隔离与去重 | 项目内按规范化 IP 合并，保留来源与原始告警；跨项目独立 |
| 触发 | 累计符合条件的未处理去重 IP 达到阈值，按配置的批大小、并发创建独立工程 |
| 指挥思路 | 直接关联“工程 → 指挥思路”，默认内置“威胁 IP 分析”；每批冻结最新内容和策略 |
| 冷却 | 从选入批次开始；冷却结束且有未覆盖新告警才再次入池 |
| 并发 | 同 IP 同时只属于一个批次；暂停批次占容量，失败批次保留 IP 占用等待人工处理 |
| 成功 | 分析任务成功且非空报告归档后整批成功 |
| 失败 | 手动重试创建新尝试与工程，使用原快照；或放弃原快照 |
| 校验 | 一条记录无效或 ID 内容冲突则整批拒绝，事务回滚 |
| 保留 | 原始告警永久保存；支持来源/接收时间清理及项目清空 |

## 模块与依赖

```text
安全设备 → intelligence-api → intelligence-store (intelligence.db)
                                  ↓
                           intelligence manager
                                  ↓ stable attempt ID
                         EngineManager / EngineStore
                                  ↓
                   专用分析会话 ← 批次告警快照
                                  ↓
                   完整报告归档 → 批次整批结算
```

| 文件 | 职责 |
| --- | --- |
| `intelligence-types.ts` | 协议、策略、模板、批次、工程输入类型与默认值 |
| `intelligence-input.ts` | 严格字段校验、IP 规范化、稳定内容摘要序列化 |
| `intelligence-store.ts` | WAL SQLite、原子接收、去重、候选占用、快照及结算 |
| `intelligence.ts` | 与传输无关的触发、工程桥接、恢复及操作 |
| `intelligence-api.ts` | 设备鉴权、正文限制、管理鉴权与接口分发 |
| `intelligence-session.ts` | 独立会话目录、能力白名单、完成校验 |
| `ThreatIntelPage.tsx` | IP、数据源、自动分析、批次、接入文档五页签 |

复用项目注册表、SQLite 适配层、工程任务及报告归档。每批用一个分析 worker 汇总全部 IP，在同一报告内完成逐 IP 告警分析与跨 IP 关联。

## 存储与接收一致性

`intelligence.db` 独立保存数据源、请求回执、事件 ID 摘要、原始告警、IP 水位、项目策略、批次及执行尝试。工程指挥思路由现有 `doctrines.ts` 统一管理，不维护第二套模板库。策略引用指挥思路 ID，创建批次时解析最新内容；找不到时暂停创建，不改变已有批次快照。原始告警使用递增接收序号，IP 主键为 `(project_id, normalized_ip)`。

Token 只保存 SHA-256 摘要，创建或轮换时返回一次。设备 Token 只绑定一个项目和数据源。接收接口位于浏览器入口验证之前，仅该精确路径使用 Token；所有管理路径仍经过浏览器入口、登录和授权声明。读完正文后重新核验凭据，避免读取期间轮换 Token 仍能写入。

先完整解析所有记录，再在 `BEGIN IMMEDIATE` 事务内保存事件、IP 汇总及回执。请求/事件 ID 在数据源内唯一，以排序后的规范化 JSON 计算摘要。相同内容重放不增加计数，不同内容返回 409 并整批回滚。正文、证据、嵌套深度、请求速率与同时推送数均有上限。

## 触发、快照与冷却

候选满足 `未覆盖的新告警 + 冷却已过 + 无批次占用`。在同一写事务内读取并发容量、按最早新告警选取、创建批次和尝试、冻结快照、占用 IP、设置冷却截止，防止重复领取。

例如阈值 20、每批 50、并行 2：积压 120 个候选时先建两批各 50 个，余下 20 个等待容量。未到阈值的尾批不会自动凑批。

每 IP 冻结 `throughSeq`。成功仅覆盖该水位以内的告警，工程期间新告警不被覆盖。没有新告警的旧 IP 不会因冷却到期自动重复触发。

批次快照每 IP 最近 10 条未覆盖告警，每条证据截取 2000 字符；初始模型输入每 IP 最近 3 条、证据 512 字符。完整原始告警保留在情报库。采样控制上下文大小，报告需说明限制。

调度在接收、策略修改和批次操作后核对，并每 5 秒补偿检查，包括冷却到期和工程完成。每轮每项目最多领取 8 批。项目并发上限与现有全局 worker 上限分别生效。

## 工程创建与恢复

两个 SQLite 库不能跨库原子提交。例如工程已保存但批次引用未写回时进程退出，重启不能再创建第二个工程。

情报库先保存执行尝试 UUID；工程库 `engine_intelligence.attempt_id` 建唯一约束。工程行、尝试关联、冻结输入与初始任务在同一事务保存后才调度，重复创建返回原工程；即使创建调用在提交后抛错，也按尝试 ID 恢复原关联。

启动及定期核对所有未结束批次，不依赖 WebSocket 通知。工程重启沿用原系统的暂停策略，须人工恢复模型执行。已知工程被删除时标记失败待重试；工程库保留尝试关联作为删除凭据，防止重新创建同一尝试。

回写校验最新尝试 ID，已结算尝试不可重复结算，旧尝试不能覆盖手动重试的新状态。

## 分析会话

专用会话位于 `intelligence-sessions/<projectId>`，只加载 `goal_progress`、`goal_complete`、`goal_blocked`，依据批次告警快照及指挥思路进行分析。禁用通用基础工具、扩展、技能、项目上下文及其他会话工具。指挥思路决定分析要求，项目策略配置执行上限。工程不可追加目标或向普通指挥官发送指令；过程在工程任务日志查看，不能按普通聊天会话打开。

报告应标明告警来源、时间、证据和采样限制，区分事实与推断，缺少信息时如实说明。手动重试新建尝试并沿用原批次快照。

## 状态与完成

```text
queued → creating → running ⇄ paused
                       ↓
           succeeded / failed / aborted
                         ↓
                  手动 retry → 新 attempt
                  或 discard → 放弃快照
```

`goal_complete` 校验目标验收条件并要求提交非空完整报告；worker 成功后工程等待报告归档，再将工程设为 completed。批次还检查工程状态、非空报告及所有任务 done，避免现有普通工程“流程结束但含失败任务”的状态误判。

失败或中止释放运行容量但保留 IP 占用；不自动重复消耗模型额度。重试受当前项目并发限制，不修改冷却起点或原输入，旧工程保留。放弃覆盖原快照水位并释放 IP，后续新告警仍可在冷却后触发。暂停占容量且不会标为已处理。

## 清理与扩展

按来源/接收时间清理前先预览，并阻止清理关联未结束或待重试批次的记录。列表从剩余事件计算计数、来源与时间。水位和幂等摘要保留，重放不会重新制造旧任务。

清空项目情报删除告警、IP 与批次，但保留数据源、策略及幂等摘要，工程指挥思路独立管理。批次快照、已建工程、报告与分析会话的保留范围在页面及接入文档说明；清空情报不等于删除独立工程中的副本。删除项目清除相应情报及凭据。

后续增加 RSS、域名或 URL：新增接入适配器与规范化能力，复用存储与桥接接口。其他任务可复用模板快照、稳定尝试关联和整批回写；候选选择由其业务模块负责，首版不提前设计通用编排系统。
